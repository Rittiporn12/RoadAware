# RoadAware — กระบวนการ Analytics และ Dashboard ระยะถัดไป

บันทึกจากข้อกำหนดผู้ใช้: 9 พฤศจิกายน 2569

## ขอบเขตและสถานะ

ผู้ใช้ต้องการงาน Advanced ที่มีกระบวนการวิเคราะห์ชัดเจน รวม Descriptive Analytics และต้องมี Dashboard สำหรับ Data Visualization ภายหลัง ขั้นตอนปัจจุบันทำฐานข้อมูลและ Notebook 01–05 เท่านั้น **ยังไม่สร้าง Dashboard หรือหน้าจอ Frontend**

Advanced ในที่นี้หมายถึงความเข้มงวดของนิยามข้อมูล การเปรียบเทียบอย่างเป็นระบบ ความพร้อมของตัวแปร การประเมินตามเวลา และการตรวจย้อนกลับ ไม่ใช่การเพิ่มความซับซ้อนของโมเดลโดยไม่มีหลักฐานว่าช่วย

## กระบวนการที่ต้องรักษา

คำถามวิเคราะห์ → นิยามหน่วยนับ/ขอบเขต → ตรวจคุณภาพ/ที่มา → เลือกวิธี → ผลพร้อมหลักฐาน → วิเคราะห์ข้อจำกัด → เชื่อมกับการตัดสินใจ

แต่ละการวิเคราะห์ต้องระบุข้อมูลที่ใช้ ช่วงปี กลุ่มที่ถูกกันออก จำนวนตัวอย่าง นิยามตัวหาร วิธีคำนวณ และไฟล์ผลลัพธ์ ต้องแยก raw กับ clean และสถิติย้อนหลังกับค่าพยากรณ์ให้ชัด

## ชั้นของ Analytics

| ชั้น | คำถาม | แนวทาง | สถานะ |
| --- | --- | --- | --- |
| Data Quality Analytics | ข้อมูลเชื่อถือได้ส่วนไหน? | schema, missingness, date ambiguity, repeated IDs, coordinate checks, lineage, reconciliation | อยู่ในงาน Notebook ปัจจุบัน |
| Descriptive Analytics | เคยบันทึกเหตุเท่าไร ที่ไหน เมื่อไร แบบใด? | สรุปรายปี/เดือน/วัน/ชั่วโมง พื้นที่ ประเภทเหตุ สภาพอากาศที่รายงาน พร้อมกราฟและจำนวนตัวอย่าง | EDA ปัจจุบันเป็นฐาน; เพิ่มสถิติหลัง cleaning เมื่อขอบเขตนิยามแล้ว |
| Diagnostic Analytics | รูปแบบต่างกันตามช่วงเวลา/กลุ่มอย่างไร? | ตารางไขว้ เปรียบเทียบวันธรรมดา/วันหยุด ฤดูกาล/เทศกาล ตรวจความเสถียรข้ามปีและผลของการคัดข้อมูล | แผนต่อยอด ต้องมีปฏิทินและข้อมูลพร้อม |
| Predictive Analytics | อนาคตจะมีจำนวนเหตุที่บันทึกเท่าไร? | Baseline เทียบ Count Regression/Boosting, temporal evaluation, feature ablation, calibration และ uncertainty ตามความเหมาะสม | ระยะโมเดลภายหลัง ยังไม่ฝึก |
| Decision Support | ผู้เดินทางควรเตรียมตัวอย่างไร? | สรุปบริเวณและลักษณะเหตุที่ควรระวัง อธิบายหน่วยและข้อจำกัด | ระยะเชื่อม Web App; ยังไม่ยืนยันลดอุบัติเหตุหรือเส้นทางปลอดภัยที่สุด |

## ประเด็นวิเคราะห์เชิงลึกที่ต้องพิจารณาในงานถัดไป

- การเปลี่ยนยอดระหว่างปีอาจเกิดจากความครบถ้วนของการรายงาน นิยาม schema หรือช่วงปีที่ไม่ครบ ต้องตรวจสิ่งเหล่านี้ก่อนอธิบายว่าอุบัติเหตุเพิ่ม/ลด
- รายชั่วโมงต้องตรวจความถูกต้องของเวลาและค่าเที่ยงคืนที่อาจเป็นค่าปริยาย รายวันต้องตรวจผลกระทบจากวันที่กำกวม
- เปรียบเทียบ 3 ปีและ 5 ปีด้วยช่วงทดสอบเดียวกัน เพื่อศึกษาผลของข้อมูลเก่าหรือการเปลี่ยนรูปแบบ ไม่เลือกช่วงจาก Final Test
- เปรียบเทียบขนาดพื้นที่และความละเอียดเวลา โดยวัดความเบาบาง จำนวนศูนย์ ความครอบคลุม ความเสถียร และความคลาดเคลื่อน ทั้งนี้ต้องกำหนดการทดลองก่อนเปิดผลทดสอบขั้นสุดท้าย
- ประวัติเหตุเมื่อฝนตกจากตารางเฉพาะอุบัติเหตุ บอกได้เพียงองค์ประกอบของเหตุที่บันทึก ไม่ใช่อัตราเกิดเหตุเมื่อฝนตก ต้องมีทุกช่วงฝน/ไม่ฝนรวมช่วงไม่มีเหตุ และตัวหารการเดินทางหากอ้างความเสี่ยงต่อการเดินทาง
- การเปรียบเทียบเทศกาลต้องกำหนดช่วงวันและตัวหาร เช่น จำนวนวัน ไม่เทียบยอดช่วง 7 วันกับทั้งเดือนตรง ๆ และยังต้องระบุข้อจำกัดเมื่อไม่มีปริมาณรถ
- ทดสอบความไวต่อกฎ cleaning และการกันข้อมูลออก พร้อมระบุว่าอาจเกิด selection bias
- การวิเคราะห์หลายกลุ่มหรือหลายสมมติฐานต้องระวังข้อสรุปจากกลุ่มเล็กและการทดสอบจำนวนมาก ระบุว่าเป็น exploratory หรือ confirmatory
- Feature importance/SHAP ถ้าเพิ่มภายหลังอธิบายพฤติกรรมโมเดล ไม่ใช่สาเหตุของอุบัติเหตุ ต้องทดสอบความสมเหตุสมผลและความเสถียรก่อนใช้เล่าเรื่อง

## Dashboard / Data Visualization — บันทึกไว้ ยังไม่ทำ

แนวคิดเบื้องต้นสำหรับตกลงรายละเอียดในระยะถัดไป:

1. ภาพรวม: จำนวนเหตุที่บันทึก ช่วงข้อมูล ความครอบคลุม และสถานะคุณภาพ แยกจำนวนแถว จำนวนรหัสเหตุ และเหตุที่ผ่านเกณฑ์
2. เวลา: แนวโน้มรายปี/เดือน heatmap วัน–ชั่วโมง และการเปรียบเทียบช่วงวันหยุด/เทศกาลเมื่อข้อมูลรองรับ
3. พื้นที่: แผนที่พร้อม legend และ unknown areas เลือกจังหวัดหรือขอบเขตที่รองรับได้ โดยไม่สื่อความละเอียดเกินข้อมูล
4. ลักษณะเหตุ: ประเภทอุบัติเหตุ สภาพทาง และบริบทที่รายงาน พร้อมจำนวนตัวอย่าง/ข้อมูลขาด
5. คุณภาพข้อมูล: missingness, quarantines, date uncertainty, duplicate conflicts และข้อมูลที่ถูกกันออก
6. ประสิทธิภาพโมเดล: Baseline vs models, predicted vs observed, bias, coverage และผลแยกช่วงเวลา หลังมีการทดลองจริง

ตัวกรองที่ต้องพิจารณา: ปี/เดือน/วัน/สัปดาห์ พื้นที่ ประเภทเหตุ และเทศกาล ใช้เฉพาะช่วงและหน่วยที่มีข้อมูล แต่ละกราฟต้องมีชื่อ หน่วย แหล่งข้อมูล ข้อจำกัด และตารางอ้างอิงที่ตรวจได้ กราฟต้องอ่านได้บนมือถือและไม่สื่อสารด้วยสีอย่างเดียว

Dashboard เชิงย้อนหลังกับหน้าวางแผนเส้นทางมีวัตถุประสงค์ต่างกัน ต้องออกแบบการเชื่อมภายหลังโดยรักษาความต่างระหว่างค่าจริงย้อนหลังกับค่าคาดการณ์

## หลักฐานและการส่งต่อ

เก็บ Notebook ที่รันจริง ตาราง CSV กราฟ PNG รายงาน JSON รุ่นข้อมูล/config และคำสั่งตรวจซ้ำใน backend/ พร้อมบันทึกการ review และ commit/push ไป GitHub เป็น checkpoint งานที่ยังไม่ได้รันต้องระบุว่า pending ไม่ใช้กราฟจำลองแทนผลจริง

เอกสารนี้เป็นแผนและบริบทสำหรับระยะถัดไป ไม่ใช่รายงานว่าการวิเคราะห์ขั้นสูงทั้งหมดหรือ Dashboard เสร็จแล้ว
