# RoadAware — เอกสารตั้งต้นโครงงานและแผนทดลองโมเดล

ฉบับ 0.1 | วันที่ 9 พฤศจิกายน 2569

สถานะ: สรุปบริบทและเสนอแผนเพื่อทำความเข้าใจร่วมกัน ยังไม่เริ่มพัฒนาเว็บ ฝึกโมเดล หรือดำเนินการทดลองตามแผนนี้

## ภาพรวมโครงงาน

RoadAware เป็นแนวคิด Web App สำหรับวางแผนการเดินทาง โดยนำข้อมูลอุบัติเหตุย้อนหลังมาพยากรณ์จำนวนเหตุที่บันทึกในพื้นที่และช่วงเวลาอนาคต แสดงผลตามแนวเส้นทางด้วยสี พร้อมสรุปลักษณะอุบัติเหตุในอดีตและข้อควรระวังที่มีหลักฐานรองรับ ออกแบบใหม่โดยเน้นมือถือและรองรับ PC

เป้าหมายระยะใกล้คือทำความเข้าใจข้อมูล กำหนดโจทย์พยากรณ์ และพิสูจน์คุณภาพโมเดลก่อนเชื่อมเป็นระบบเว็บเต็มรูปแบบ

### สิ่งที่ผู้ใช้ยืนยันแล้ว

- ใช้ Regression เพื่อคาดการณ์จำนวนอุบัติเหตุจากประวัติย้อนหลัง โดยสนใจข้อมูล 3–5 ปี
- ค้นหาต้นทาง–ปลายทาง แสดงเส้นทางและบริเวณที่ควรระวังด้วยสี
- ต้องการคำอธิบายลักษณะอุบัติเหตุ เวลา ฝน การจราจร ฤดูกาล และเทศกาล เท่าที่ข้อมูลรองรับ
- ออกแบบ UX/UI ใหม่ทั้งหมด เน้นมือถือ พร้อมรองรับ PC
- ใช้ RoadAware_2rd เป็นแนวทางและเลือกใช้เฉพาะส่วนที่เหมาะสม
- ขั้นตอนปัจจุบันจัดทำเอกสาร 5 หัวข้อและแผนโมเดลเท่านั้น รอคำสั่งขั้นตอนถัดไป

### ข้อเสนอที่ยังไม่ได้ตกลงเป็นข้อกำหนดสุดท้าย

- เริ่มพิสูจน์แนวคิดด้วยการพยากรณ์รายวันล่วงหน้า 1 วัน แล้วจึงประเมินการขยายเป็น 7 วันหรือช่วงเวลาย่อย
- เลือกพื้นที่นำร่องและหน่วยพื้นที่จากความครบถ้วนของข้อมูล เปรียบเทียบแนวทางกริดกับช่วงถนนก่อนตัดสินใจ
- ยังไม่รับรองการพยากรณ์ระดับชั่วโมง ความน่าจะเป็นรายบุคคล หรือการเลือกเส้นทางที่ปลอดภัยที่สุด

## 1. ปัญหาที่ต้องการแก้

ข้อมูลประวัติอุบัติเหตุช่วยบอกว่าเคยเกิดเหตุที่ไหนและเมื่อใด แต่ผู้เดินทางต้องการข้อมูลประกอบการตัดสินใจสำหรับการเดินทางที่กำลังจะเกิดขึ้น เช่น ช่วงใดของเส้นทางควรระวัง มีประวัติเหตุแบบใด และเงื่อนไขของวันที่จะเดินทางสัมพันธ์กับจำนวนเหตุอย่างไร

โจทย์ของ RoadAware คือเปลี่ยนข้อมูลย้อนหลังให้เป็นการพยากรณ์ที่ระบุพื้นที่ ช่วงเป้าหมาย และเวลาที่ออกคำพยากรณ์ชัดเจน แล้วนำเสนอให้อ่านเข้าใจง่ายบนเส้นทางจริง

คำถามวิจัยเริ่มต้น:

1. โมเดลพยากรณ์จำนวนเหตุที่บันทึกในอนาคตได้ดีกว่าค่าเฉลี่ยย้อนหลังของพื้นที่หรือไม่?
2. ปฏิทิน วันหยุด และข้อมูลประวัติที่พร้อมใช้จริงช่วยเพิ่มคุณภาพเพียงใด?
3. การเพิ่มอากาศหรือปริมาณจราจรช่วยได้หรือไม่ เมื่อควบคุมเวลาเผยแพร่ข้อมูลแล้ว?
4. หน่วยพื้นที่และช่วงเวลาแบบใดละเอียดพอสำหรับผู้ใช้ และยังมีข้อมูลเพียงพอสำหรับทดสอบ?

ผลลัพธ์หลักคือ “จำนวนเหตุที่คาดว่าจะมีการบันทึกต่อพื้นที่–ช่วงเวลา” ซึ่งยังไม่เท่ากับจำนวนเหตุทั้งหมดที่เกิดจริง หรือโอกาสที่ผู้ใช้หนึ่งคนจะประสบอุบัติเหตุ ต้องมีข้อมูลปริมาณการเดินทางและการประเมินเพิ่มเติมหากจะเปลี่ยนเป็นอัตราความเสี่ยงดังกล่าว

## 2. ผู้ใช้เป้าหมาย / Impact / SDG

### ผู้ใช้เป้าหมายที่เสนอ

| กลุ่ม | ความต้องการ | ลำดับความสำคัญ |
| --- | --- | --- |
| ผู้เดินทางด้วยรถยนต์ส่วนบุคคล โดยเฉพาะเส้นทางไม่คุ้นเคย | ตรวจช่วงที่ควรระวังและเตรียมตัวก่อนเดินทาง | กลุ่มหลักสำหรับออกแบบรุ่นแรก |
| ผู้วางแผนเดินทางไกลหรือช่วงเทศกาล | ดูบริบทของวันเดินทางและสำรวจทางเลือกที่ระบบรองรับ | กลุ่มหลัก |
| นักวิจัยหรือผู้วิเคราะห์ความปลอดภัยทางถนน | ตรวจรูปแบบเชิงพื้นที่–เวลาและผลประเมินโมเดล | กลุ่มรอง; ยังไม่ออกแบบเป็นระบบหน่วยงานเต็มรูปแบบ |

ยังไม่อ้างว่าโมเดลเดียวรองรับความเสี่ยงเฉพาะรถจักรยานยนต์ รถบรรทุก หรือผู้เดินเท้า ต้องประเมินข้อมูลแยกก่อน

### ผลกระทบที่คาดหวังและวิธีวัด

- ช่วยให้ผู้ใช้รู้จุดและลักษณะเหตุที่ควรระวังก่อนเดินทาง วัดด้วยความเข้าใจในการอ่านผลและการระบุช่วงสำคัญ
- ช่วยประกอบการวางแผน วัดด้วยการทดสอบภารกิจค้นหาเส้นทางและอ่านคำอธิบายบนมือถือ รวมถึงเวลาและอัตราทำภารกิจสำเร็จ
- ทำให้ข้อมูลและคำพยากรณ์ตรวจสอบได้ วัดความเข้าใจเรื่องสี พื้นที่ไม่มีข้อมูล และความแตกต่างระหว่างประวัติกับคำทำนาย
- การลดจำนวนอุบัติเหตุเป็นผลกระทบระยะยาวที่ต้องศึกษาภาคสนามเพิ่มเติม ไม่อนุมานจากคะแนนโมเดลหรือความพึงพอใจเพียงอย่างเดียว

### SDG ที่เกี่ยวข้อง

- **SDG 3 สุขภาพและความเป็นอยู่ที่ดี — เป้าประสงค์ 3.6:** เกี่ยวข้องกับการลดการเสียชีวิตและบาดเจ็บจากอุบัติเหตุทางถนน โครงงานสนับสนุนด้านข้อมูลเพื่อการป้องกัน ไม่ได้วัดผลสำเร็จของเป้าประสงค์โดยตรง ข้อความเป้าประสงค์ดั้งเดิมบนหน้า UN ระบุปี 2020 จึงไม่เขียนเปลี่ยนเป็นปี 2030 โดยไม่มีบริบทอ้างอิง [แหล่ง UN](https://sdgs.un.org/goals/goal3)
- **SDG 11 เมืองและชุมชนที่ยั่งยืน — เป้าประสงค์ 11.2:** เชื่อมโยงด้านการเดินทางและความปลอดภัยบนถนน เป็นความสอดคล้องเชิงแนวคิด ไม่ใช่การวัดตัวชี้วัดการเข้าถึงขนส่งสาธารณะ 11.2.1 [แหล่ง UN](https://sdgs.un.org/goals/goal11)

ข้อมูลเพิ่มเติมที่ต้องตรวจหรือจัดหาในขั้นถัดไป:

- ปฏิทินวันหยุดและเทศกาลรายปี รวมวันหยุดชดเชย พร้อมแหล่งยืนยันและขอบเขตช่วงเทศกาล
- โครงข่ายถนนอิสระจากรายการอุบัติเหตุ เพื่อกำหนดช่วงถนนและจับคู่พิกัดให้ถูกถนน
- อากาศพยากรณ์ที่มีทั้งเวลาออก forecast และเวลาที่ forecast มีผล หากต้องการใช้ฝนในคำพยากรณ์
- ปริมาณจราจร/การเดินทางและความครอบคลุม หากต้องการวิเคราะห์ผลของรถมากหรืออัตราเหตุต่อการเดินทาง; ขณะนี้ยังไม่ได้ยืนยันว่ามีข้อมูลพร้อม
- นิยามวันเวลา รหัสเหตุ เวลาเผยแพร่/แก้ไข และขอบเขตการรายงานจากผู้เผยแพร่ รวมถึง metadata และเงื่อนไขใช้งานของรุ่นไฟล์ที่จะนำเข้า

### แนวทางเก็บข้อมูลที่เสนอ

เก็บ raw แบบไม่เขียนทับ แยก interim, processed และ reports พร้อมทะเบียนแหล่งข้อมูล รุ่นไฟล์ วันที่รับข้อมูล และ checksum เก็บความเชื่อมโยงจากแถวที่จัดเตรียมกลับไปยังต้นฉบับ รวมทั้งธงข้อมูลขาด/ขัดแย้ง ขั้นนี้ยังไม่คัดลอกชุดข้อมูลเดิมหรือสร้างฐานข้อมูลใหม่

## 4. AI Task โมเดลเบื้องต้น และแผนทดสอบ

### 4.1 นิยามงาน

**AI Task: การพยากรณ์จำนวนเหตุเชิงพื้นที่–เวลา ด้วย Count Regression**

- หนึ่งตัวอย่าง = หนึ่งพื้นที่ × หนึ่งช่วงเป้าหมาย
- y = จำนวนเหตุที่บันทึกตามนิยามการนับที่ตรวจสอบแล้วในพื้นที่และช่วงนั้น
- ผลทำนาย = ค่าเฉลี่ยจำนวนเหตุที่คาดหมาย จึงมีทศนิยมได้และต้องไม่ติดลบ
- ต้องบันทึก issue time, target start/end และข้อมูลที่พร้อมใช้ก่อน issue time
- แปลงค่าพยากรณ์เป็นระดับสีภายหลัง โดยกำหนดเกณฑ์บน Train/Validation แล้วล็อกก่อนทดสอบขั้นสุดท้าย
- แยกสถิติย้อนหลัง ลักษณะเหตุ และคำแนะนำ ออกจากค่าคาดการณ์ ไม่อ้างคำอธิบายเชิงเหตุและผลจากความสัมพันธ์เพียงอย่างเดียว

ข้อเสนอเริ่มต้นคือพยากรณ์รายวันล่วงหน้า 1 วัน ส่วนการเลือกกริดหรือช่วงถนนและขนาดพื้นที่ต้องดูความหนาแน่น ความครบถ้วน และผลทดลองก่อน ไม่มีการยืนยันหน่วย 1 กม., 2 กม. หรือ 5 กม. สำหรับระบบใหม่ในขั้นนี้

| อากาศ | ฝน อุณหภูมิ | ค่าเป้าหมายต้องมาจาก forecast ที่พร้อมก่อน issue time; reanalysis ของวันเป้าหมายใช้วิเคราะห์ย้อนหลังเท่านั้น |
| การจราจร | ปริมาณรถหรือค่าคาดการณ์ | เพิ่มเมื่อมีแหล่งข้อมูลและตรวจความพร้อมแล้ว; ETA จาก router ไม่เท่ากับปริมาณรถ |

ไม่ใช้จำนวนผู้เสียชีวิต บาดเจ็บ สาเหตุ หรือลักษณะการชนของเหตุในช่วงเป้าหมายเป็นตัวแปรทำนาย เพราะเป็นข้อมูลหลังเหตุ ประวัติสรุปของตัวแปรเหล่านี้อาจศึกษาแยกได้เมื่อผ่านเกณฑ์ความพร้อมข้อมูล

### 4.3 โมเดลเบื้องต้นที่เสนอให้เปรียบเทียบ

| วิธี | บทบาท |
| --- | --- |
| ทำนายศูนย์ทุกพื้นที่–วัน | ตัวตรวจว่าคะแนนรวมดูดีเพราะข้อมูลส่วนใหญ่ไม่มีเหตุหรือไม่ ไม่ใช่โมเดลที่จะเลือกจาก MAE อย่างเดียว |
| ค่าเฉลี่ยย้อนหลังรายพื้นที่ และค่าเฉลี่ยตามวันในสัปดาห์เมื่อมีข้อมูลพอ | Baseline ที่โมเดลต้องแสดงประโยชน์เหนือกว่า พร้อมกำหนด fallback จาก Train |
| Poisson Regression | โมเดลตั้งต้นสำหรับจำนวนครั้งและอธิบายความสัมพันธ์เบื้องต้น |
| HistGradientBoostingRegressor โดยใช้ Poisson loss | ทดสอบความสัมพันธ์ที่ไม่เป็นเส้นตรงและปฏิสัมพันธ์ของตัวแปร |

Poisson Regression และ Gradient Boosting แบบ Poisson มีตัวอย่างและเอกสารทางการรองรับ [ตัวอย่าง count regression](https://scikit-learn.org/stable/auto_examples/linear_model/plot_poisson_regression_non_normal_loss.html), [เอกสาร HGB](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.HistGradientBoostingRegressor.html)

ยังไม่เลือกโมเดลชนะหรือรับช่วงน้ำหนักโมเดลเก่ามาใช้ทันที หากพบปัญหาการกระจายข้อมูลจึงค่อยเสนอวิธีเพิ่มเติมตามหลักฐาน ไม่เพิ่มโมเดลซับซ้อนโดยไม่มีผลทดลองรองรับ

### 4.4 ลำดับงานทดลองที่เสนอ — ยังไม่ได้ดำเนินการ

1. **ตรวจข้อมูล:** schema รายปี นิยามหนึ่งเหตุ รหัสซ้ำ วันเวลา พิกัด ความครอบคลุม และการเผยแพร่ล่าช้า โดยเฉพาะรายการวันที่ยังไม่ชัดและปี 2569 ที่ไม่มีรหัส
2. **กำหนดสัญญาการพยากรณ์:** พื้นที่ศึกษา หน่วยพื้นที่ ช่วงเป้าหมาย ระยะล่วงหน้า issue time และแหล่งตัวแปรที่ใช้ได้จริง
3. **สร้างตารางพื้นที่–เวลา:** มีช่วงที่ไม่พบเหตุด้วย แต่ศูนย์หมายถึงไม่พบการบันทึกภายในขอบเขตที่นิยามไว้ ไม่แทนพื้นที่หรือช่วงที่ไม่มีข้อมูลด้วยศูนย์
4. **ล็อกแผนประเมิน:** Train → Validation → Final Test ตามเวลา; เตรียมหลายรอบเลื่อนเวลาเพื่อดูความสม่ำเสมอ และเว้นระยะตาม horizon/ความพร้อมคำตอบเท่าที่จำเป็น
5. **ฝึก Baseline และโมเดลตั้งต้น:** preprocessing เรียนรู้จาก Train; ตั้งค่าและเลือกโมเดลด้วย Validation เท่านั้น ใช้ early stopping แบบเคารพลำดับเวลาหรือปิดการแบ่งภายในแบบสุ่ม
6. **เพิ่มตัวแปรทีละกลุ่ม:** ปฏิทิน → ประวัติที่พร้อมใช้ → อากาศ/จราจรที่ผ่านเกณฑ์ แล้ววัดว่าช่วยตรงไหนจริง
7. **ตรวจข้อผิดพลาดและความไม่แน่นอน:** ดูพื้นที่ที่ทำนายสูง/ต่ำเกิน ช่วงเทศกาล วันธรรมดา เดือน และพื้นที่ข้อมูลน้อย ใช้การเปรียบเทียบเป็นช่วงเวลาที่รักษาการพึ่งพากันของข้อมูล
8. **ล็อกโมเดลและเกณฑ์สี:** ประเมินขั้นสุดท้ายตาม protocol ที่กำหนดก่อนเห็นผล หากยังไม่มีข้อมูลทดสอบอิสระให้รายงานข้อจำกัดและเก็บคำพยากรณ์ล่วงหน้าเพื่อประเมินภายหลัง
9. **พิจารณาเชื่อมเว็บ:** เมื่อผ่านเกณฑ์ที่ตกลงแล้ว ให้ตรวจว่าผล API และแผนที่ตรงกับโมเดลและไม่แสดงเกินความละเอียดจริง

การแบ่งตามเวลาเป็นหลักสำคัญในการไม่ฝึกด้วยอนาคตแล้วไปวัดกับอดีต [เอกสาร scikit-learn](https://scikit-learn.org/stable/modules/cross_validation.html#time-series-split)

**ข้อจำกัดจากงานเดิม:** ปี 2568 เคยถูกใช้ทดสอบและ Validation เคยถูกใช้ซ้ำ จึงไม่เรียกชุดเดิมว่าไม่เคยเห็นสำหรับงานปรับโมเดลใหม่ ปี 2569 มีนิยามหน่วยนับต่างกันและข้อมูลไม่เต็มปี จึงยังไม่แต่งตั้งเป็น Final Test โดยอัตโนมัติ

### 4.5 ตัวชี้วัดและเกณฑ์ที่ต้องตกลงก่อนทดลอง

| มิติ | วิธีตรวจที่เสนอ |
| --- | --- |
| ความคลาดเคลื่อนจำนวนเหตุ | MAE, RMSE และ Mean Poisson Deviance โดยตรวจค่าทำนายบวกตามข้อกำหนด metric |
| ยอดรวมและความลำเอียง | ยอดคาดการณ์เทียบยอดบันทึก รายเดือนและรายพื้นที่; แสดงทั้งยอดเกินและยอดขาด |
| การชี้พื้นที่ที่ควรให้ความสำคัญ | สัดส่วนเหตุที่อยู่ในกลุ่มพื้นที่คะแนนสูงสุดตามสัดส่วนที่กำหนดบน Validation เทียบ Baseline |
| ความสม่ำเสมอ | ผลแยกเดือน เทศกาล พื้นที่ และช่วงจำนวนเหตุ; ไม่สรุปจากคะแนนรวมเดียว |
| ความไม่แน่นอน | ประเมินความผันผวนของผลต่างจาก Baseline; ถ้าแสดงช่วงพยากรณ์ ต้องทดสอบ coverage และความกว้างก่อน |
| ความครอบคลุม | จำนวนพื้นที่/ช่วงเวลาที่ให้ผลได้ พื้นที่นอกขอบเขต และข้อมูลที่ถูกกันออกพร้อมเหตุผล |

ไม่ใช้ Accuracy แบบจำแนกประเภทเป็นคะแนนหลัก และไม่กำหนดเป้าหมาย “แม่น 90%” โดยไม่มีนิยาม ไม่ใช้ MAPE เป็นหลักเมื่อคำตอบมีศูนย์จำนวนมาก

เกณฑ์ผ่านที่เสนอ: ผลเหนือกว่า Baseline อย่างสม่ำเสมอในตัวชี้วัดหลักที่เลือกไว้ก่อน ไม่เกิดจากพื้นที่หรือเดือนเดียว ยอดรวมไม่มีอคติที่ยอมรับไม่ได้ ไม่พบข้อมูลอนาคตรั่วเข้าโมเดล และจัดการพื้นที่ไม่ทราบได้ถูกต้อง ตัวเลขเกณฑ์และขอบเขตที่ยอมรับยังต้องกำหนดหลังตรวจข้อมูลก่อนเปิดผลทดสอบ

หลักฐานที่ต้องเก็บเมื่อเริ่มทดลอง: รุ่นข้อมูล กฎ cleaning รายการ features และเวลาที่พร้อมใช้ ช่วง Train/Validation/Test การตั้งค่าโมเดล random seed เวอร์ชันไลบรารี ผลพยากรณ์รายตัวอย่าง ตารางเปรียบเทียบ และข้อจำกัด ทุกการทดลองต้องระบุสิ่งที่รันจริงและสิ่งที่ยังไม่ได้รัน

## 5. แนวคิด Web App

### เส้นทางการใช้งาน

ผู้ใช้กรอกต้นทาง–ปลายทางและวันเวลา → ระบบหาเส้นทาง → เชื่อมเส้นทางกับพื้นที่และคำพยากรณ์ที่ใช้ได้ → แสดงแผนที่และสรุป → ผู้ใช้เลือกบริเวณเพื่ออ่านประวัติเหตุและข้อควรระวัง

- มือถือใช้แผนที่คู่กับแผงด้านล่างที่ย่อ–ขยายได้ ส่วน PC ใช้แผงข้างแผนที่
- แสดงระดับสีพร้อมข้อความกำกับ เกณฑ์และหน่วยชัดเจน พื้นที่ไม่มีข้อมูลใช้สีเทาและบอกเหตุผล
- แยก “ประวัติที่ผ่านมา” “ค่าคาดการณ์” และ “ข้อควรระวัง” พร้อมวันอัปเดตและความครอบคลุม
- ข้อควรระวังเริ่มจากข้อความที่ตรวจทานและผูกกับหลักฐาน ไม่จำเป็นต้องมี Generative AI เพื่อเขียนทุกคำตอบ
- หากโมเดลรายวัน การเปลี่ยนเวลาในวันเดียวกันต้องไม่ทำให้ UI สร้างความต่างปลอม; การเปรียบเทียบเวลาออกเดินทางเปิดเมื่อรองรับและทดสอบแล้ว
- ไม่กระจายยอดกริด–วันให้เป็นคำทำนายถนนรายชั่วโมงโดยไม่มีโมเดลหรือสมมติฐานที่ประเมินรองรับ วงกลมบนแผนที่ต้องไม่สื่อความละเอียดเกินจริง
- มีสถานะโหลด ค้นหาไม่พบ เชื่อมต่อไม่ได้ และข้อมูลไม่เพียงพอ โดยไม่ล้างข้อมูลที่ผู้ใช้กรอก

### จุดต่างที่ต้องสร้างและแสดงหลักฐาน

RoadAware มุ่งเน้นคำพยากรณ์ที่ระบุช่วงอนาคตชัด อธิบายประวัติเหตุจากข้อมูลไทย และเปิดเผยแหล่งข้อมูล ความครอบคลุม และผลทดสอบ ผู้ใช้จึงตรวจได้ว่าสีและคำอธิบายมาจากอะไร

Waze มี crash-history alerts อยู่แล้ว และ Google Maps มีการนำทาง/รายงานเหตุ จึงไม่อ้างว่าการแสดงจุดเสี่ยงเป็นสิ่งที่บริการเหล่านั้นไม่มี หรือว่า RoadAware ปลอดภัยกว่าโดยยังไม่พิสูจน์ ความสามารถและการให้บริการของผลิตภัณฑ์อื่นอาจต่างตามพื้นที่และอุปกรณ์ [Waze](https://support.google.com/waze/answer/13014546?hl=en), [Google Maps](https://support.google.com/maps/answer/9770907?hl=en-CA)

### ขอบเขตขั้นตอนปัจจุบันและสิ่งที่ยังต้องตัดสินใจ

รอบนี้ส่งมอบเอกสารบริบทเท่านั้น ยังไม่ฝึกหรือเลือกโมเดล ไม่สร้าง Web App ไม่ deploy และไม่เปลี่ยนข้อมูลเดิม

การตัดสินใจสำหรับขั้นต่อไปเมื่อผู้ใช้สั่ง: พื้นที่นำร่อง, ช่วงปีที่จะใช้, หน่วยและความละเอียดการพยากรณ์, horizon, นิยามการนับและความพร้อมข้อมูล, ตัวชี้วัดหลักและแผนทดสอบอิสระ รวมถึงแหล่งอากาศ/จราจรที่จะใช้จริง
